## 已拍板的設計決策（2026-09-17）

1. **A／B／C 必須同時出現在第一屏。** 原本大字版在所有手機上選項 C 都落在首屏之外，會讓作答偏向 A、B，直接傷害結果可信度。現在選項主標為 21–25px 粗體、補充說明 16px，仍屬大字，但 375×620（iPhone SE 在 LIFF 內）到 430×800 的每一題全部首屏可見。此規則寫在 `aieq.html` 的 CSS 註解中，之後調整字級必須重新量測。

4. **正式 PWA icon。** 黑底、螢光粉紅「AI」、螢光綠重點線、白色「人格誌」，向量原稿 `assets/aieq/pwa/icon.svg`，主體在 maskable 安全區內。manifest 的 scope 收斂為 `/aieq`。
5. **單一證據的軸不宣稱「很明顯」。** J／P 只有一題，結果頁顯示「這次偏 X（只有一題，僅供參考）」。

## 階段 1.5：題庫升級為 8 題（完成）

為什麼做：7 題版的 J／P 只靠第 7 題，三個選項有兩個判給 J。用真實計分引擎窮舉全部作答組合的結果：

| | 7 題 | 8 題 |
|---|---|---|
| J／P 在所有作答組合中的分布 | 67／33 | 56／44（與其他三軸一致） |
| 作答略有雜訊時，真 J 被判對 | 85.0% | 81.3% |
| 作答略有雜訊時，真 P 被判對 | 60.0% | 75.0% |
| 最常見／最少見類型（平均應為 6.3%） | 11.4%／2.9% | 9.5%／3.9% |

雜訊模型：每題 60% 選最符合自己的選項、25% 選中間選項、15% 選相反選項。這些數字量的是**穩定度與權重偏誤**，不是效度；題目是否真的量到 J／P 需要真人資料（階段 4-5）。

設計規則（日後加題或改權重時適用）：

- 同一軸兩題的強選項權重不可相同。引擎把總分剛好為 0 的平手判給右極（I／N／F／P），第 8 題若與第 7 題同為 ±2 會讓分布翻成 J 33／P 67。第 8 題因此用 ±3。
- 搞怪要平均分配在三個選項。只有一個選項特別好笑時，它會因為好笑而被選，量到的就不是人格。
- 每個選項都不能讓人覺得「選了丟臉」，尤其 P 選項不可寫成懶散。
- 改動後 `test/aieqBalance.test.ts` 必須通過：每個字母佔 40–60%、16 型皆可達且單一類型 3.5–10%、任一軸不會剛好為 0、真 J／真 P 判對率皆 ≥72%。

連動修改：版本字串 `ai-personality-1.1-8q`；首頁「8 SCENARIOS / ABOUT 1 MIN」「八個日常情境」；結果頁的「只有一題，僅供參考」改為依實際證據數顯示（答「不確定」導致某軸只剩一題時仍會出現）；會議 ENTP 範例測試補上第 8 題的 P 答案，公式驗證不變。

資料相容性：`present()` 會以現行題庫重新計分舊 session，因此本次升級刻意排在 staging 部署之前，沒有任何既有作答資料。**上線後若再改題庫，必須先實作依 `instrument_version` 分流計分。**

已知限制：第 8 題的「再來三個」可能同時沾到一點 N（愛探索可能性），需真人資料確認。

**第 8 題目前是暫定題。** `AI-PERSONALITY-LIFF-GAME-DEVELOPMENT-PLAN.md`（2026-09-13）第 0 階段寫明正式八題要整合 Eve 哥提供的完整題目與選項，並要求「題庫與計分版本綁定 session」。現行的 `q08_ai_options` 是在那份題目到位之前，為了修正 J／P 偏誤而加的；Eve 哥的八題定稿後，需逐題對照、重跑 `aieqBalance.test.ts`，並在那之前先完成依 `instrument_version` 分流計分。

### 「多級」朋友圈：朋友的朋友（2026-09-18 已上線 staging）

威廷同意後實作：可見範圍三級（`private`／`friends`／`friends_of_friends`，migration 015），預設不變；朋友圈頁有「讓朋友的朋友也看得到我」開關，**開啟的人才看得到別人的二度人脈**（互相看見）；二度人脈只回傳暱稱、頭像、類型與動物，並標示「經由誰・幾位共同好友」；重新確認結果不會把已開啟的人降級；連結中間的朋友刪除資料後，其朋友隨之消失。以上皆由 integration 測試覆蓋。原始理由保留如下。

建議做「朋友的朋友」，但必須是**被看見的人自己選擇開啟**：可見範圍由兩級（只有自己／朋友）增為三級（＋朋友的朋友），預設維持「朋友」。二度人脈只顯示暱稱、頭像、動物與類型，並標示「經由誰認識、幾位共同好友」；不顯示雷達圖與解讀。理由：LINE 暱稱與頭像是個資，現行護欄是「雙方同意才互相看見」，未經同意曝光給陌生人會破壞信任，也有個資法風險。邀請樹不需另外開發：`aieq_friend_invites` 已記錄邀請人與接受者，可直接統計每人帶來幾位朋友，僅作成效分析、不做獎勵。
