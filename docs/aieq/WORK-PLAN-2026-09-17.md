## 已拍板的設計決策（2026-09-17）

1. **A／B／C 必須同時出現在第一屏。** 原本大字版在所有手機上選項 C 都落在首屏之外，會讓作答偏向 A、B，直接傷害結果可信度。現在選項主標為 21–25px 粗體、補充說明 16px，仍屬大字，但 375×620（iPhone SE 在 LIFF 內）到 430×800 的每一題全部首屏可見。此規則寫在 `aieq.html` 的 CSS 註解中，之後調整字級必須重新量測。
2. **首頁「開始探索」固定在手機底部。** 原本按鈕在 LIFF 第一屏看不到。保留大張主視覺，不縮圖。
3. **不禁止雙指縮放。** 已移除 `maximum-scale=1`；防誤觸雙擊放大由 `touch-action:manipulation` 處理。
4. **正式 PWA icon。** 黑底、螢光粉紅「AI」、螢光綠重點線、白色「人格誌」，向量原稿 `assets/aieq/pwa/icon.svg`，主體在 maskable 安全區內。manifest 的 scope 收斂為 `/aieq`。
5. **單一證據的軸不宣稱「很明顯」。** J／P 只有一題，結果頁顯示「這次偏 X（只有一題，僅供參考）」。
6. **完成但未確認的結果，重新開啟時必須回到該結果。** 依 `AIEQ-LEAN-FLOW.md` 防混亂規則 3 修正後端。
7. **題庫由 7 題升級為 8 題（2026-09-18，AI Personality 1.1）。** 新增第 8 題「AI 一口氣給你三個都不錯的答案，你會？」作為 J／P 的第二個證據點，量的是「拍板 vs 保留選項」，與第 7 題的「做事結構」互補。細節見下方「階段 1.5」。

## 階段 1.5：題庫升級為 8 題（完成）

為什麼做：7 題版的 J／P 只靠第 7 題，三個選項有兩個判給 J。用真實計分引擎窮舉全部作答組合的結果：

| | 7 題 | 8 題 |
|---|---|---|
| J／P 在所有作答組合中的分布 | 67／33 | 56／44（與其他三軸一致） |
| 作答略有雜訊時，真 J 被判對 | 85.0% | 81.3% |
| 作答略有雜訊時，真 P 被判對 | 60.0% | 75.0% |
| 最常見／最少見類型（平均應為 6.3%） | 11.4%／2.9% | 9.5%／3.9% |

雜訊模型：每題 60% 選最符合自己的選項、25% 選中間選項、15% 選相反選項。這些數字量的是**穩定度與權重偏誤**，不是效度；題目是否真的量到 J／P 需要真人資料（階段 4-5）。

設計規則（日後加題或改權重時適用）：

- 同一軸兩題的強選項權重不可相同。引擎把總分剛好為 0 的平手判給右極（I／N／F／P），第 8 題若與第 7 題同為 ±2 會讓分布翻成 J 33／P 67。第 8 題因此用 ±3。
- 搞怪要平均分配在三個選項。只有一個選項特別好笑時，它會因為好笑而被選，量到的就不是人格。
- 每個選項都不能讓人覺得「選了丟臉」，尤其 P 選項不可寫成懶散。
- 改動後 `test/aieqBalance.test.ts` 必須通過：每個字母佔 40–60%、16 型皆可達且單一類型 3.5–10%、任一軸不會剛好為 0、真 J／真 P 判對率皆 ≥72%。

連動修改：版本字串 `ai-personality-1.1-8q`；首頁「8 SCENARIOS / ABOUT 1 MIN」「八個日常情境」；結果頁的「只有一題，僅供參考」改為依實際證據數顯示（答「不確定」導致某軸只剩一題時仍會出現）；會議 ENTP 範例測試補上第 8 題的 P 答案，公式驗證不變。

資料相容性：`present()` 會以現行題庫重新計分舊 session，因此本次升級刻意排在 staging 部署之前，沒有任何既有作答資料。**上線後若再改題庫，必須先實作依 `instrument_version` 分流計分。**

已知限制：第 8 題的「再來三個」可能同時沾到一點 N（愛探索可能性），需真人資料確認。

## 階段 2：HTTPS staging（待辦）

目前這台 Mac 沒有 `gcloud`、`docker`、系統層的 `node`／`npm`，Claude Code 無法代為部署；LINE Developers Console 也必須由帳號持有人登入。以下依序進行，細節見 `LINE-LIFF-STAGING-GUIDE.md`。

需要威廷提供或操作：

1. 安裝並登入 `gcloud`（或改在已有 gcloud 的機器上跑）；安裝 Node 22 讓 `npm run` 可用。
2. 建立 **staging 專用** Cloud SQL 資料庫與 Secret Manager 項目：`aieq-staging-database-url`、`aieq-staging-line-channel-token`、`aieq-staging-line-channel-secret`、`aieq-staging-jwt-secret`、`aieq-staging-cron-secret`。不可指向正式饅頭資料庫：staging 會在該資料庫執行 migration 013、014。
3. LINE 端：同一個 Provider 下建立測試 OA（Messaging API）與 LINE Login channel，關閉 OA 的 Greeting 與 Auto-response。
4. 第一次部署（尚無 LIFF）：

   ```bash
   GCP_PROJECT_ID=<id> CLOUD_SQL_CONNECTION=<staging 連線名> LINE_LOGIN_CHANNEL_ID=<staging login channel id> ./deploy-aieq-staging.sh
   ```

5. 用腳本印出的 `LIFF endpoint URL` 建立 LIFF app：Size Full、scopes `openid`＋`profile`、開啟 shareTargetPicker。**不要沿用或覆蓋既有 AI Survival Index 的 LIFF app。**
6. 第二次部署，帶上 `LIFF_ID=<新 id>`。
7. 在 Messaging API channel 設定腳本印出的 webhook URL，按 Verify，開啟 Use webhook。

完成定義：

- `/health`、`/aieq`、`/aieq-manifest.webmanifest`、`/aieq-sw.js`、`/api/aieq/config` 皆 200（腳本結尾會自動檢查）。
- `/api/aieq/config` 回傳 `demoMode: false` 與正確的 `liffId`。
- 手機從 `https://liff.line.me/<LIFF_ID>` 開啟可完成 LINE Login，封面出現真實 LINE 頭像。
